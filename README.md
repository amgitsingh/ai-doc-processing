# AI Customer Complaint & Case Processing System

## Problem Statement

Businesses receive customer complaints through many different document formats and channels — emails, uploaded PDFs, scanned forms saved as `.docx`, plain-text logs — and reviewing each one manually to identify the customer, categorize the issue, draft a response, and brief the internal team does not scale. Delays in this process mean slower resolutions, inconsistent customer communication, and no systematic view of case status across a growing backlog.

## Solution Overview

This project is a batch-oriented, LLM-powered pipeline that automatically processes a folder of customer complaint documents and produces, for every document:

1. **Structured case data** — a validated, schema-enforced extraction of the customer's details, complaint category, issue, resolution, and case status (not a raw LLM text dump).
2. **A professional customer response email** — grounded strictly in the extracted case data, never inventing details the source document didn't contain.
3. **An internal case summary** — a five-part briefing (overview, key issue, action taken, current status, recommended next action) for the support/management team.

The three AI tasks are explicitly composed as separate steps in a LangChain workflow (extraction → parallel email + summary generation), not one large prompt — and the whole batch runs with real document-level concurrency via `chain.batch()`, not a naive sequential loop. Every document is processed independently with its own error handling, so one corrupted or unreadable file never stops the rest of the batch. Results are written as structured JSON, plain-text emails and summaries, and one consolidated CSV report for a quick, scannable overview of the entire batch.

## Architecture

```
data/ (complaint_*.txt / .pdf / .docx)
        │
        ▼
┌───────────────────────┐
│    Document Loader     │   src/loaders/document_loader.py
│  (per-file try/except; │   load_documents()
│   bad files logged &   │
│   skipped, not fatal)  │
└───────────┬────────────┘
            │  List[LoadedDocument]
            ▼
┌───────────────────────┐
│   Extraction Chain      │   src/components/extraction.py
│  (Pydantic-validated,   │   get_extraction_chain()
│   batched across docs)  │
└───────────┬────────────┘
            │  CaseRecord.case: ComplaintCase
            ▼
┌─────────────────────────────────────────────────┐
│      RunnableParallel — per document, batched     │
│  ┌────────────────────┐   ┌────────────────────┐  │
│  │    Email Chain       │   │   Case Summary      │  │
│  │  email_generator.py  │   │  case_summary.py    │  │
│  └────────────────────┘   └────────────────────┘  │
└───────────────────────┬───────────────────────────┘
                         │  CaseRecord.email / .case_summary
                         ▼
              ┌─────────────────────┐
              │    Output Writers     │   src/pipeline/output_writer.py
              └──────────┬──────────┘
         ┌────────────────┼───────────────────┬─────────────────────┐
         ▼                ▼                   ▼                     ▼
  output/            output/             output/               output/
  structured_data/   customer_emails/    case_summaries/       final_report.csv
  (.json per doc)    (.txt per doc)      (.txt per doc)        (one row per doc)
```

Cutting across every stage: `src/utils/config_loader.py` + `.env` supply the LLM provider/model settings, and `src/utils/logger.py` writes a timestamped `INFO`/`ERROR` trail for every stage to `logs/app.log`, so a failure at any point (loading, extraction, or generation) is both handled gracefully in code and visible in the log — never a silent failure.

## Tech Stack

- **Python 3.12**
- **LangChain** (`langchain`, `langchain-openai`, `langchain-google-genai`) — LLM orchestration: prompt templates, native structured output, `RunnableParallel`, `.batch()`
- **Pydantic** — schema validation for extracted case data (`ComplaintCase`)
- **pandas** — building the consolidated `final_report.csv`
- **pypdf** / **python-docx** — text extraction from `.pdf` / `.docx` complaint documents
- **python-dotenv** — loading API keys and provider selection from `.env`
- **OpenAI or Google Gemini** (your choice, via `LLM_PROVIDER`) — the underlying LLM

## Environment Variables (`.env`)

| Variable | Required | Description |
|---|---|---|
| `LLM_PROVIDER` | Yes | `"openai"` or `"gemini"` — selects which provider is used everywhere in the pipeline |
| `OPENAI_API_KEY` | If provider is `openai` | Your OpenAI API key |
| `GEMINI_API_KEY` | If provider is `gemini` | Your Google Gemini API key |

## How to Run

```bash
python src/main.py
```

No arguments needed. This will:
1. Load every supported file (`.txt`, `.pdf`, `.docx`) from `data/`
2. Extract structured case data for each document
3. Generate a customer email and internal case summary for each
4. Write `output/structured_data/`, `output/customer_emails/`, `output/case_summaries/`, and `output/final_report.csv`
5. Log progress and any errors to both the console and `logs/app.log`

To process your own documents, add `.txt`/`.pdf`/`.docx` files to `data/` before running — no code changes needed.

## Key Design Decisions

- **Native structured output (`llm.with_structured_output(ComplaintCase)`) over manual parsing.** The extraction schema is enforced by the provider itself, not recovered from free-form text after the fact — this directly satisfies "should not simply save the raw LLM response" rather than just approximating it.
- **`Optional[str] = None` for fields that may genuinely be absent** (`customer_name`, `email`, `phone_number`, `resolution_provided`). A required-string schema would pressure the model into inventing a plausible value just to satisfy validation. Verified this actually works: `complaint_005_malformed.txt`, which never mentions a name or contact, correctly comes back with those fields `null` — not a fabricated guess.
- **`complaint_category` is a plain `str`, not a Python `Literal`**, with the allowed values injected into the prompt from `config.json`. Adding or renaming a category is a config edit, not a code change.
- **`RunnableParallel` for email + case summary generation.** Both depend only on the extracted case, not on each other, so they run concurrently per document rather than as two sequential LLM calls — the explicit "workflow orchestration, not one big LLM call" requirement made concrete in code, not just described.
- **`chain.batch(..., return_exceptions=True)` for document-level concurrency**, on top of the within-document parallelism above. Measured on the 5 sample documents: ~3x faster end-to-end (23s → 6.9s) than a sequential loop, with the same per-document error isolation a `try/except` loop would give — one failing document never aborts the rest of the batch.
- **A plain `CaseRecord` dataclass carries each document through the pipeline**, rather than forcing this file-based project into a pandas DataFrame from the start. `pandas` is only used at the very end, to build `final_report.csv` — the natural tool for that specific job, not the backbone of the whole pipeline.
- **Nothing is dropped silently.** A document that fails extraction or generation still gets an output artifact in every writer — `structured_data` shows `case: null` with the error, `customer_emails`/`case_summaries` show a placeholder explaining why, and `final_report.csv` shows `False`/`False` success flags with the error message, rather than the document just vanishing from the output.
- **The customer email structurally cannot see internal-only fields.** `escalation_required` and `supporting_document_available` aren't just "asked not to be mentioned" in the email prompt — they're absent from that chain's input entirely, so there's nothing for the model to leak even by accident. The internal case summary, by contrast, is explicitly given both.

## Known Limitations

- **No retry logic for transient API failures.** A network blip during a batch call marks that document as failed for the run; re-running `main.py` reprocesses the entire `data/` folder from scratch (including documents that already succeeded), rather than resuming only the failed ones.
- **No deduplication across runs.** Output files are named by input stem, so re-running the pipeline simply overwrites the previous output for the same filename — there's no tracking of "already processed" documents.
- **`complaint_category` isn't validated against `config.json`'s label list in code**, only guided via the prompt — the model is asked to pick from the provided categories but nothing structurally rejects an unlisted value if it doesn't.
- **Tested at small scale.** The pipeline has been verified end-to-end against 6 sample documents (4 real + 2 deliberate edge cases), not hundreds — `max_concurrency=5` is a reasonable default for this scale, not a value tuned against real provider rate limits at higher volume.
- **English-only.** Both the expected input documents and all generated output (emails, summaries) assume English; no language detection or localization.
- **No automated test suite.** Verification throughout development was done via real, end-to-end runs against the sample data (see `IMPLEMENTATION_PLAN.md` for the step-by-step record) rather than `pytest`-based unit tests — appropriate for this project's scope, but not something that would scale to a larger codebase without one.
